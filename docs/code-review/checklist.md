# 代码核查清单

本清单是逐段读代码的入口；评分和留档格式见[评审记录模板](../reviews/template.md)。它补充现有八类工程规范，不替代它们。先对照当前 OpenSpec 场景，再逐类核查；每个判断都写明代码证据、测试或扫描手段。证据不足时标为未知，不推定通过。

## 第一层：七类代码

每一类都回答四件事：代码想保证什么、实际靠什么机制保证、什么情况下会失效、需要怎样修正。

|类别|必须检查的问题|主要依据|
|---|---|---|
|接口入口|参数类型/范围/枚举是否白名单校验？身份与资源归属是否在服务端检查？返回字段是否符合 DTO 合同？|OpenSpec 场景；[后端规范](../standards/backend.md)、[安全规范](../standards/security.md)|
|业务逻辑|实现是否逐条对应需求与验收场景？状态迁移是否完整？是否违反已定规则？|OpenSpec 正式规约及当前变更|
|数据库操作|多步写入是否处于正确事务？唯一性是否由约束保障而非“先查再写”？迁移是否可重复、可恢复？|[数据规范](../standards/data.md)、对应数据合同|
|公共函数|是否存在复制逻辑或不一致实现？错误是否被吞掉？抽象是否覆盖真实共性？|调用点、同类实现及错误路径|
|错误处理|每种失败是否有明确出口和正确响应？是否泄露内部错误、路径、凭据或配置？|[后端规范](../standards/backend.md)、[安全规范](../standards/security.md)|
|安全与隐私|是否校验用户输入、转义输出、隔离主体数据并保护敏感字段？是否有水平/功能越权？|[安全规范](../standards/security.md)、[数据规范](../standards/data.md)|
|性能|是否有循环内查询、无索引筛选或无界列表？排序和游标是否稳定？是否有测量证据？|对应查询合同；[测试规范](../standards/testing.md)、[运维规范](../standards/ops.md)|

适用性要写明理由。例如当前内存合成仓储没有 SQL 事务或索引，数据库项可标“不适用（本次代码无数据库读写）”；不能由此推断将来的持久化设计已经通过。

## 第二层：七个评审维度

每个维度使用“已覆盖 / 部分覆盖 / 未覆盖”或“有证据 / 有风险 / 未知”，并附文件、行段、测试名或命令。最终总评三选一：**可用**、**需要修改**、**风险无效**。

1. 需求覆盖：规约中的相关场景是否有实现和验证？
2. 一致性：页面、接口、数据合同、状态流转是否相符？
3. 失败路径：错误输入、依赖故障、并发/重放等是否有明确行为？
4. 查询性能风险：循环查询、索引、分页、排序及测量证据如何？
5. 重复代码：重复逻辑位置、影响和修复条件是什么？
6. 安全漏洞：输入、输出、身份、归属、日志、秘密和依赖风险如何？
7. 高风险场景：并发、事务、权限、迁移、恢复或外部调用会怎样失效？

## 结论与准入

- **可用**：本次范围内的适用检查有证据，未发现阻断问题；仍可记录边界和后续风险。
- **需要修改**：发现可复现的不一致或缺口；修复后对受影响范围复查并链接修复提交。
- **风险无效**：核心保证缺失，或现有结构无法支持目标要求；合并前必须重做方案。

每个面向 `main` 的 PR 都需要新增或更新 `docs/reviews/` 下的评审记录。CI 只检查记录存在和字段齐全；维护者仍须读评审依据。记录必须如实标注自审、脚本发现或独立同伴复核，单人自审不能写成交叉评审。代码在记录之后又发生变化时，须重新检查受影响部分。
